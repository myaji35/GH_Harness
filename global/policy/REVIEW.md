# REVIEW.md — 하네스 검증(CHECK 축)·코드 리뷰 기준

> 2026-10-26 도입. 근거: Anthropic, "How the Claude Code team does code review"(2026-10-16).
> 목표: **사람 확인 시간을 가장 적게 쓰되, 되돌림·사고가 늘지 않게.** 지표는 대표님 확인 횟수와 되돌린 커밋 수.

## 1. 위험 등급 — 작성자가 아니라 변경이 정한다
| 등급 | 예 | 확인 |
|---|---|---|
| 낮음 | 문서·문구, 테스트만, 스크립트 주석, 플래그 뒤 추가 기능 | 자동 검사(LINT_CHECK·RUN_TESTS) 통과면 끝 |
| 보통 | 일반 기능·버그 수정, 뷰, 마이그레이션 없는 모델 변경 | 자동 검사 + check-harness 1회 |
| 높음 | 인증·권한·개인정보, 결제·광고비, 배포 설정(`config/deploy*`, `Dockerfile`, `.kamal/`), DB 마이그레이션, CI·hook 자체, 고객에게 나가는 문구 | 자동 검사 + check-harness + **대표님 확인(T2)** |

- 한 변경에 여러 등급이 섞이면 가장 높은 등급.
- 에이전트의 "통과" 보고는 대표님 확인을 대신하지 않는다. 승인은 그 커밋 하나에만 유효하다(새 커밋이면 다시).
- 판정은 `tests/evals/review_tier.py` 의 경로 규칙과 같다(평가 세트로 고정).

## 2. 지적은 등급을 붙인다
- **중요(Important)**: 동작이 틀리거나 데이터·돈·권한에 영향. 고쳐야 통과.
- **사소(Nit)**: 이름·형식. PR당 최대 3개, 통과를 막지 않는다.
- **원래 있던 문제(Pre-existing)**: 이번 변경이 만든 게 아님. 막지 않고 별도 이슈로.
- 요약은 개수로 시작: "중요 2 · 사소 0 · 원래 있던 1". 없으면 없다고 쓴다.

## 3. 증거
- 모든 지적은 파일:줄과 그 경로를 타는 코드를 인용한다. "위험해 보임"은 지적이 아니다.
- "통과"는 실행한 명령과 출력으로 보인다. 구현자의 통과 주장은 근거가 아니다.

## 4. 반복 상한
- 같은 원 이슈(`source_issue`)에 대한 수정(`*_FIX`)은 **3회까지**. 넘으면 `on_complete.sh` 가 더 만들지 않고
  `HERMES_CONSULT`("접근 방식 재검토")로 넘긴다.
- 두 번째 리뷰부터는 바뀐 부분(diff)만 본다. 이미 낸 지적은 반복하지 않는다. 같은 종류의 버그는 종류로 한 번에 지적한다.

## 5. 사고는 평가 세트가 된다
- 되돌린 커밋·사고·대표님이 지적한 오판은 `tests/evals/cases/*.json` 에 사례로 넣는다.
- 하네스 hook·모드 파일·라우팅을 바꿀 때마다 `bash tests/evals/run.sh` 를 돌려 점수가 떨어지지 않았는지 본다.
