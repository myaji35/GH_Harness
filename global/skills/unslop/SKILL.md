# Unslop (글의 AI 티 제거)

> 출처: open-pstack `unslop` (MIT, NOTICE.md). GH_Harness 규칙에 맞게 옮김.

글을 고쳐 AI 패턴을 없앤다. 아래 패턴을 훑은 뒤 다시 쓴다. **뜻은 지키고, 의도한 어조에 맞춘다.**

- 한국어 글: 아래 "한국어 AI 티" 를 적용한다.
- 영어 글: `references/english-rules.md`(원문 규칙, 번호 3~33)를 적용한다. 다른 스킬이 규칙 번호로 인용하므로 번호는 바꾸지 않는다.
- 하네스 글 규칙은 그대로 따른다: 대표님 호칭, 한국어 보고, 완료 보고는 1~2문장 + 핵심 수치.

**예외 — 의도된 과장은 지우지 않는다.** 유튜브 썸네일·후킹 카피처럼 대표님이 "과해야 읽힌다"고 정한 산출물(전역 CLAUDE.md "영상·산출물 보여주기")은 강조·숫자·물음표가 목적이다. 그 경우는 본문 설명·보고만 다듬고 카피 자체는 건드리지 않는다.

## 한국어 AI 티

### 1. "~것입니다" · "~할 수 있습니다" 반복
문장 끝이 같은 틀로 줄줄이 이어진다. 명사화(`~하는 것`)를 풀고 동사로 끝낸다.
- 전: "이 기능은 사용자가 쉽게 찾을 수 있도록 하는 것입니다. 이를 통해 이탈을 줄일 수 있을 것입니다."
- 후: "검색창을 위로 올렸다. 첫 화면 이탈이 줄 것으로 본다(다음 주 측정)."

### 2. 번역투
- `~에 있어서`, `~에 대한`, `~을 통해`, `~로 인해` 남발 → 조사 하나로 줄이거나 동사로.
- `~를 가지고 있다` → `~가 있다`. `~되어지다`(이중 피동) → `~되다` 또는 능동.
- `가장 ~한 것 중 하나` → 그냥 `~하다` 또는 순위를 밝힌다.
- `그것은`, `그들은` 같은 대명사 주어 → 주어를 빼거나 이름을 쓴다.
- `~의 ~의 ~의` 연쇄 → 문장을 쪼갠다.
- 전: "결제 모듈에 있어서의 오류 처리에 대한 개선을 통해 안정성을 가지게 되었습니다."
- 후: "결제 모듈의 오류 처리를 고쳐 실패율이 3.1%에서 0.4%로 줄었다."

### 3. 피동·주어 숨기기
`~가 진행되었습니다`, `~이 확인되었습니다`, `~가 적용되었습니다` → 누가 했는지 밝힌다. 보고에서는 "제가 X 를 했습니다", 문서에서는 행위자(스크립트·hook·사람)를 주어로.
- 전: "배포가 진행되었으며 정상 동작이 확인되었습니다."
- 후: "kamal 로 배포했고 `/health` 가 200 을 반환한다."

### 4. 부풀린 한자어·외래어
`활용하다`→`쓰다`, `수행하다`→`하다`, `진행하다`(아무 동사 대신)→실제 동사, `제고`→`높이기`, `도모`→뺀다, `구축하다`(작은 일에)→`만들다`, `레버리지`·`시너지`·`인사이트`·`솔루션`·`고도화`·`최적화`(측정 없이)→ 구체 행동이나 숫자.

### 5. 과한 강조
- 굵은 글씨를 문장마다 쓰지 않는다. 한 화면에 정말 놓치면 안 되는 것 한두 개만.
- `매우`, `정말`, `핵심적인`, `획기적인`, `혁신적인`, `완벽하게`, `강력한` → 지우거나 숫자로.
- 느낌표·장식 이모지·⭐ 남발 → 뺀다(문서 안에 이미 있는 관례 표시는 유지).
- 줄표(—) 로 문장을 계속 이어 붙이지 않는다. 끊어서 두 문장으로.

### 6. 불필요한 목록화
두세 문장이면 되는 내용을 불릿으로 쪼개지 않는다. `첫째/둘째/셋째` 처럼 항목을 억지로 셋으로 맞추지 않는다(실제 개수만큼). "**성능:** 성능이 개선되었습니다" 처럼 굵은 머리말이 다음 문장을 그대로 반복하는 목록은 문장으로 바꾼다. 비교·여러 수치는 표가 낫다.

### 7. 빈 서두·맺음
`좋은 질문입니다`, `말씀하신 대로`, `물론입니다`, `도움이 되셨길 바랍니다`, `궁금한 점 있으시면 말씀해 주세요`, `결론적으로`·`요약하자면`(바로 앞 내용 반복), `앞으로가 기대됩니다` → 지운다. 결론이 필요하면 다음 행동이나 숫자를 쓴다.

### 8. 얼버무림과 막연한 출처
- `~일 수도 있을 것 같습니다`, `~로 보여질 수 있습니다` → `~이다` 또는 `~로 본다(근거: …)`. 모르면 "확인 안 됨" 이라고 쓴다.
- `전문가들은`, `업계에서는`, `일반적으로` → 출처를 대거나 지운다.

### 9. "단순히 X 가 아니라 Y" · 느낌 문장
`단순한 도구가 아니라 파트너입니다` 같은 대비 틀, `더욱 편리하게`, `한층 스마트하게` 처럼 느낌만 있는 문장 → 무엇이 어떻게 바뀌는지(기능·수치)를 쓴다. 다른 프로젝트 문서에 그대로 붙여도 말이 되는 문장이면 이 프로젝트에 대해 아무 말도 안 한 것이다. 지운다.

### 10. 유의어 돌려쓰기 · 과잉 경어
한 단락에서 `고객/사용자/이용자/회원` 을 번갈아 쓰지 않는다. 하나로 고정. `~해 드리겠습니다`, `~하시는 것을 권장드립니다` 를 매 문장에 쓰지 않는다. 대표님 보고는 정중하되 짧게: "X 했습니다. 결과 Y."

### 11. 압축 기호체
`원인: X → 결과: Y, 조치 ✅` 처럼 화살표·기호로만 이어 붙인 문장은 읽는 사람이 해독해야 한다. 표나 완결된 문장으로 쓴다(짧은 상태 표의 칸 안은 괜찮다).

## 절차

1. 대상 글 전체를 읽고 패턴 번호를 붙여 표시한다.
2. 뜻·사실·숫자·고유명사·코드·경로는 그대로 두고 다시 쓴다.
3. 고친 글을 다시 한 번 훑어 새로 들어간 AI 티가 없는지 본다.
4. 대표님이 고친 이유를 원하면 "패턴 번호 → 고친 곳" 을 한두 줄로 붙인다. 원하지 않으면 고친 글만 낸다.

글 파일(.md 등)을 고치는 건 문서 작업이므로 직접 한다. 코드 안의 문자열·주석·UI 카피를 바꾸는 건 코드 변경이므로 Codex 에 위임한다(`codex e --skip-git-repo-check -s workspace-write "<파일 경로 + 바꿀 문구 전/후>" < /dev/null` → `git diff` 검수).
