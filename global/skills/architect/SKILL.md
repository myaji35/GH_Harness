# Architect (설계 스케치 → 구현)

> 출처: open-pstack `architect` (MIT, NOTICE.md). GH_Harness 규칙에 맞게 옮김.

타입, 함수 시그니처, 클래스 모양, 모듈 경계를 `not implemented` 본문과 의사코드로 스케치한다. 여러 모델 관점을 합쳐 하나를 고른 뒤, 그 스케치를 계약으로 코드를 채운다.

할 일 목록에 단계별 항목을 먼저 연다: 1 근거 2 스케치 3 합의 4 구현 5 폐기.

## A. 근거 잡기

새 코드가 닿는 모든 시스템의 머릿속 모델을 만든다. 관련 서브시스템에 `how` 스킬을 돌려 그 스킬이 정한 구조 설명을 만든다. 파일 이름을 대는 건 근거가 아니다. 설계가 소유권·계층을 다시 정의하면 기존 모양에 `why` 스킬도 돌려, 그 이유를 추측이 아닌 제약으로 삼는다.

주변 시스템이 전혀 없는 완전 신규일 때만 A 를 건너뛴다.

## B. 스케치

`arena` 스킬을 설계 스케치 과제 + A 의 근거 자료로 돌린다. 후보마다 `references/runner-prompt.md` 를 프롬프트로 준다.

**후보(runner) 구성** — 원본의 pstack 모델 시트·provider-dispatch 대신 아래를 쓴다.

| 후보 | 실행 | 출력 위치 |
|---|---|---|
| A — Claude | `Agent` 도구(`general-purpose`), 부모 모델, `run_in_background` | `<scratchpad>/architect-<slug>/candidate-claude/` |
| B — Codex | `codex e --skip-git-repo-check -s workspace-write -C <후보 전용 디렉터리> "<runner-prompt + 과제 + 근거 경로>" < /dev/null` (Bash `run_in_background`) | `<scratchpad>/architect-<slug>/candidate-codex/` |

- 후보는 저장소가 아니라 **각자 전용 디렉터리**에 설계 패키지(타입 스케치·시그니처·모듈 지도·근거 문서)를 쓴다. 저장소에 Codex 를 둘 이상 띄우지 않기 위해서다. 저장소 파일을 직접 고치게 하지 않는다.
- Codex 로그인이 안 되면(`codex login status`) 탈락으로 기록하고 Claude 후보를 서로 다른 설계 방향 2개로 띄운다. 몰래 대체하지 않는다.
- 시크릿이 든 파일은 Codex 에 보내지 않는다.

**두 번 설계한다.** 첫 안이 충분해 보여도 합치기 전에 구조가 다른 후보를 최소 2개 요구한다(exhaust-the-design-space). 한 모양 안의 부분 수정이 아니라 전체 모양의 대안이어야 한다.

합치기 전에 모든 후보를 `references/design-red-flags.md` 로 걸러 본다. 다음 기여자는 열어 본 파일만 보고, 가장 가까운 예시를 베끼고, 컴파일되는 최단 경로를 택하는 에이전트라고 가정한다. 한 파일에서 맞아 보이는 변경이 저장소 전체에서도 맞는 설계를 고른다.

살아남은 후보는 **인터페이스 깊이**로 비교한다. 더 작고 단순한 공개 면 뒤에 더 많은 복잡도를 숨기는 설계를 고른다.

arena 는 합쳐진 설계 패키지 하나를 돌려준다. 그 합성 결정이 근거 문서의 "Synthesis decision" 절을 채운다.

## C. 합의 (선택)

기본: 체크포인트 없이 합쳐진 설계로 바로 구현한다(되돌릴 수 있는 작업 — T0).

대표님이 "설계 보여주고 멈춰", "구현 전에 보여줘" 처럼 명시하면 합쳐진 설계를 보여 주고 멈춘다. 설계가 되돌릴 수 없는 방향 전환(아키텍처 패러다임 변경·기술 스택 교체·핵심 기능 삭제)이면 T2 DIRECTION 으로 `request-user-confirm.sh` 를 쓴다.

스케치는 어느 쪽이든 별도 커밋("뼈대 먼저")으로 남길 수 있다. 채우는 동안 계획된 범위의 깨짐은 괜찮다. 구현 전에 설계를 공격받고 싶으면(대표님 요청 시) `interrogate` 를 합쳐진 스케치에 돌린다.

대표님이 모양에 반대하면(체크포인트에서든 나중이든) 그걸 A 의 새 근거로 삼아 다시 근거를 잡고 B 를 다시 돌린다.

## D. 스케치대로 구현 — Codex 위임

1. **위임** — 스케치를 저장소에 반영하고 `not implemented` 본문을 채우는 일은 Codex 에 맡긴다:
   `codex e --skip-git-repo-check -s workspace-write "<정확한 파일 경로 + 스케치 문서 경로 + 채울 함수 목록 + 지켜야 할 불변식>" < /dev/null`
2. **검수** — `git diff` 로 정확성·범위·회귀·규칙 위반·과잉 변경을 본다. 스케치에서 벗어난 부분은 흘려보내지 말고 신호로 드러낸다. 스케치에 없던 매개변수가 필요해졌다면 스케치가 틀렸는지, 요구를 놓쳤는지, 구현이 넘친 건지 따진다.
3. **직접 검증** — 타입 체크·테스트·실제 실행을 내가 돌린다. Codex 의 "완료" 보고는 근거가 아니다.
4. **재위임** — 결함은 직접 고치지 않고 구체 수정 지시로 Codex 에 다시 맡긴다. 같은 저장소에서 Codex 는 한 번에 하나. 상세: `opus-codes` 스킬.

## E. 설계가 틀렸으면 폐기

스케치가 흡수하지 못하는 마찰이 구현 내내 계속되면 스케치를 버린다. 틀린 설계에 땜질하지 않는다(redesign-from-first-principles, fix-root-causes).

신호는 개별 사례가 아니라 **패턴**이다.

- 서로 무관한 코드에서 같은 모양의 우회가 반복된다.
- 무관한 엣지 케이스 여러 개가 모두 특수 분기를 요구한다.
- 컴파일하려면 탈출구(`any`, 캐스트, 실제로는 늘 채워지는 optional 필드)가 필요하다.
- 스케치는 공유 상태가 없다고 했는데 "락이 필요하다"는 반사가 나온다.
- 호출자가 추상화를 쓰려면 내부 규칙을 알아야 한다.
- D 에서 같은 모양의 이탈이 독립적으로 두 번 이상 나온다.

판단은 한다. 엣지 케이스 몇 개로 설계를 버리지 않는다. 데이터의 복잡함은 설계의 복잡함이 아니다.

폐기할 때: (1) 만든 것에 `how` 를 다시 돌린다 (2) 새 제약이 처음부터 있었다고 보고 다시 설계한다 (3) 더하기 전에 뺀다 — 새 스케치는 커지기 전에 옛것보다 작아야 한다 (4) B 로 돌아가 arena 를 다시 돌린다.

## 산출물

호출자 사용 예를 먼저 쓰고 타입 스케치를 거기서 끌어낸다. 작은 변경은 새 타입·시그니처 파일 하나, 큰 작업은 모듈 지도 + 타입 정의. 근거 문서는 `references/rationale-template.md` 형식으로 함께 낸다(사용 예·합성 결정 포함).

완료 증거는 on_complete result 의 `proof[{cmd,exit_code,output}]` (타입 체크·테스트·실행 명령과 실제 출력). 보고는 한국어로 짧게: 고른 설계와 이유, 탈락한 후보, 검증 결과.
