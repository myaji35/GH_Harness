# Blast radius (영향 범위)

> 출처: open-pstack `blast-radius` (MIT, NOTICE.md). GH_Harness 규칙에 맞게 옮김.

변경이 다른 곳을 깨뜨리는지 배포 전에 찾는다.

`how` 는 코드가 무엇을 하는지, `why` 는 왜 그 모양인지, blast-radius 는 **다른 어디를 깨뜨리는지** 답한다.

호출처 목록을 뽑는 게 일이 아니다 — grep 하면 1초다. 일은 **grep 이 안 보여 주는 고장**을 찾는 것이다.

## 내 보고서를 믿지 않는다

그럴듯한 영향 분석 글은 쓸모없다. 참이든 아니든 똑같이 설득력 있게 읽힌다. 그래서 글을 넘기지 않는다. 전체가 기대는 사실 한두 개를 찾아 **코드를 돌려** 증명한다(하네스 prove-it-works 와 같은 원칙).

### 얼마나 확실한가

변경의 안전이 기대는 사실마다, 싸게 갈 수 있는 데까지 아래로 내려가고 어디서 멈췄는지 말한다.

1. 내가 그렇다고 했다. 그 자체로는 무가치.
2. 줄을 가리켰다. 실제 `file:line` 또는 라이브러리 자체 소스.
3. 나쁜 경우가 일어날 수 없음을 보였다. 실패를 단계별로 따라갔고 닿지 않는다.
4. 돌려 봤다. 실제 코드를 호출하고 틀리면 크게 실패하는 스크립트·테스트.
5. 돌아가는 앱에서 재현했다.

4단계는 보통 앱이 쓰는 같은 라이브러리를 import 해 걱정되는 바로 그 함수를 부르는 작은 스크립트 하나다.

## 절차

1. **변경 읽기.** diff, 추가·변경·삭제한 심볼, 이제 다르게 하는 것(diff 가 말하지 않는 부분 포함). PR·커밋·이슈는 `why` 스킬 2단계(코드 앵커: `git log`, `gh pr view`, registry ISS-NNN)로 가져온다.
2. **안전의 근거인 사실 하나를 찾는다.** 위험해 보이는 변경 대부분은 사실 하나 때문에 안전하다(예: "이 호출은 이미 죽은 캐시 항목만 지우고 다른 일은 안 한다"). 그 사실이 서면 위험 경우 대부분이 한꺼번에 해소된다. 긴 '혹시' 목록 대신 여기에 시간을 쓴다.
3. **grep 이 멈추는 곳을 본다.** 호출하는 라이브러리 소스를 읽고, 고정 버전과 로컬 패치를 확인한다. 언제 도는지 따진다: microtask, unmount·정리 단계, Solid 대 React. 심볼 검색이 놓치는 것을 따라간다: API 가 돌려주는 JSON, DB 컬럼, 전송 형식, 같은 바이트를 읽는 다른 언어, feature flag, 세 단계 아래 코드. 하네스에서는 hook 스크립트(`.claude/hooks/*.sh`)가 같은 registry.json·파일을 읽는지도 본다.
4. **위험마다 정직하게.** 실제 발생 가능성과 실제 비용을 붙인다. 확인된 위험은 남기고, 확인 후 해소된 것은 따로 적는다. `why` 와 같은 규칙: 실제 `file:line` 인용, 빈 검색 결과도 답이다, 호출처·API 를 지어내지 않는다.
5. **사실 하나를 증명한다.** 실제 코드를 돌리는 스크립트·테스트로 증명한다. 하네스 규칙상 코드 작성은 Codex 에 위임한다:
   ```bash
   codex e --skip-git-repo-check -s workspace-write "<scratchpad 경로>/prove_<주제>.<ext> 를 만들어라. <정확한 import 경로>의 <함수>를 실제로 호출해 '<증명할 사실>'이 거짓이면 0 이 아닌 코드로 끝나게 하라. 다른 파일은 건드리지 마라." < /dev/null
   ```
   → 만든 스크립트를 내가 읽어 검수한다(실제 코드를 부르는가, 항상 통과하는 가짜 검사가 아닌가) → **내가 직접 실행**해 출력을 붙인다. 결과는 `proof[{cmd, exit_code, output}]` 형식으로 남긴다. Codex 를 쓸 수 없으면(`which codex` 실패) 직접 짜지 말고 그렇다고 보고하고 3단계에서 멈춘다.
6. **크거나 넓은 변경**이면 여러 모델에 같은 질문을 던져 합친다. 모델마다 다른 실제 버그를 잡는다. 하네스에서는 `interrogate` 스킬(Claude + Codex 교차 검토)을 쓰거나, 최소한 `codex e --skip-git-repo-check -s read-only "<같은 질문>" < /dev/null` 를 한 번 더 돌린다.

### 고장을 찾았을 때

이 스킬의 기본 산출물은 분석과 증명이다. 고치기까지 지시받았거나 지시 범위 안이면:
**Codex 에 구체적 수정 지시로 위임 → `git diff` 로 검수(정확성·범위·회귀·과잉 변경) → 5단계 스크립트·테스트를 내가 다시 실행해 검증.** 검수에서 결함을 찾으면 직접 고치지 않고 Codex 에 재위임한다. 같은 저장소에서 Codex 를 동시에 여러 개 돌리지 않는다.

## 돌려줄 것 (한국어)

- **무엇을 하나.** 바뀐 것, 뻔하지 않은 부분 포함.
- **안전의 근거인 사실 하나.** 서술하고, 몇 단계까지 갔는지, 증명(명령·exit code·출력)을 보인다. 증명 못 했으면 **미증명**이라고 쓴다.
- **위험.** 각각 어떻게 깨지나, `file:line`, 가능성·피해, 확인 방법. 중요한 것은 증명을 붙인다.
- **해소됨.** 확인했고 왜 괜찮은지.
- **병합 전에.** 실제 버그를 잡는 가장 싼 테스트·재현, 내가 쓴(위임해 만든) 스크립트 포함.

쉬운 말로 쓰고, 실제 코드를 인용하고, 외부로 나가기 전에 사적 정보를 지운다.

**답변:** 위 보고서. 안전의 근거인 사실은 증명됨 또는 미증명으로 표시한다.
