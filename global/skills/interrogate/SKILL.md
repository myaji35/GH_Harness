# Interrogate (멀티 모델 교차 검토)

> 출처: open-pstack `interrogate` (MIT, NOTICE.md). GH_Harness 규칙에 맞게 옮김.

설정된 모델마다 검토자 1명을 띄워 변경을 공격적으로 검토한다. 반대 신호는 역할극(persona)이 아니라 **모델의 다양성**에서 나온다. 산출물은 종합 판정이다. **변경을 자동 적용하지 않는다.**

하네스 정책과의 관계: v6 는 같은 모델의 자기 재검증을 금지하고 "다른 모델이 만든/본 결과의 교차 검증"만 남긴다. 이 스킬이 그 교차 검증이다. 그래서 대표님이 요청했을 때(또는 이슈 `payload.full_verify: true`)만 쓴다.

## 검토자 구성

| 검토자 | 실행 | 비고 |
|---|---|---|
| A — Claude | `Agent` 도구, `subagent_type: general-purpose`(또는 `Explore`), model 지정 없음(부모 모델) | 읽기 전용 지시 |
| B — Codex | `codex exec -s read-only -C <repo> -o <출력파일> "<프롬프트>"` | ChatGPT 로그인 필요(`codex login status`) |

- 모델·로그인이 안 되면 **탈락(dropout)으로 기록**하고 남은 검토자로 진행한다. 가장 가까운 모델로 몰래 대체하지 않는다 — 교차 동의의 의미가 사라진다.
- Codex 는 외부 서비스로 코드를 보낸다. 시크릿이 들어간 파일·diff 는 보내지 않는다(secret-guard 정규식으로 먼저 걸러 본다). 의심되면 그 검토자는 탈락 처리.
- 두 검토자는 한 번에 동시에 띄운다(Agent 호출과 codex Bash 를 같은 응답에서; codex 는 `run_in_background`).

## 1단계 — 범위

- 대표님이 파일·diff 를 지정하면 그것.
- 아니면 최근 작업: `git diff`(미커밋) 또는 `git diff <base>...HEAD`, 또는 해당 이슈의 `files`.
- 검토자가 이해하는 데 필요한 주변 파일을 함께 묶는다.

## 2단계 — 의도

검토자를 띄우기 전에 대표님 발화·커밋 메시지·이슈 제목/payload·코드로 의도를 한 단락으로 적는다. 의도가 정말 불명확할 때만 묻는다(대부분은 이슈에서 나온다).

## 3단계 — 검토자 실행

`references/reviewer-prompt.md` 템플릿에 의도·diff/파일·`references/rubric.md`·`references/code-quality-review.md` 를 채워 **모든 검토자에게 같은 프롬프트**를 준다. 검토자에게 파일을 고치지 말라고 명시한다.

## 4단계 — 종합

모든 검토자의 발견을 파싱한다. 같은 문제를 다르게 쓴 것은 합치고, 어느 모델이 냈는지 적는다. **두 모델 이상이 독립적으로 낸 발견이 가장 강한 신호다.** 한 모델만 낸 것도 읽되 그만큼 가중한다. 한 모델이 지적하고 다른 모델이 명시적으로 반대하면 판정의 맥락으로 남긴다.

## 5단계 — 리드 판정

리드(나)는 중립 집계자가 아니라 실용적인 시니어 엔지니어다. `references/lead-judgment.md` 를 읽고, 모든 발견을 네 칸 중 하나에 넣는다(낸 모델 + 한 줄 근거).

- **반영할 것(Act on)** — 실제 목표 기준으로 정확성·보안·유지보수에 영향. 실제 PR 이라면 막을 문제.
- **고려할 것(Consider)** — 타당하나 지금 고칠 비용을 넘는지 확신 없음. 대표님이 볼 가치.
- **참고(Noted)** — 기술적으로 맞지만 지금은 조치 불요.
- **기각(Dismissed)** — 틀림·트집·맥락 부족. 짧은 이유.

판정은 diff 만 본 검토자가 못 본 호출 체인을 직접 따라가서 한다(가정적 null → 실제 호출부 확인).

## 출력 (한국어)

```
### 의도
> (2단계 단락)

### 검토자
- 검토자 A: <모델>, 발견 N건
- 검토자 B: <모델 또는 탈락 사유>, 발견 N건

### 반영할 것
### 고려할 것
### 참고
### 기각
### 동의 지도  (어디서 모델들이 같았고 갈렸는지, 그 패턴이 말해 주는 것)
```

반영할 것이 있으면 보고 끝에 이슈화 여부를 판단한다: 대표님 지시 범위 안의 작업이면 FIX_BUG 로 바로 처리, 범위 밖이면 보고만 한다.
