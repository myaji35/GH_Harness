# Arena (후보 경쟁 → 바탕 선택 → 접붙이기)

> 출처: open-pstack `arena` (MIT, NOTICE.md). GH_Harness 규칙에 맞게 옮김.

## arena 와 RACE_MODE — 언제 무엇

하네스에는 이미 RACE_MODE(`race-dispatch.sh` → `race-judge.sh`, `docs/race-mode-design.md`)가 있다. 둘 다 "여러 모델이 같은 과제를 독립적으로 푼다"지만 목적이 다르다.

| | **RACE_MODE** | **arena** |
|---|---|---|
| 대상 | 코드 구현(GENERATE_CODE 등 이슈) | 판단이 필요한 산출물: 설계 스케치(`architect`), 문서·계획·프롬프트·카피, 정답이 하나가 아닌 작은 코드 |
| 실행 | 이슈 타입 `RACE_MODE`, provider 별 git worktree(`race/<ISS>/<provider>` 브랜치)에서 CLI 가 직접 구현 | 후보마다 전용 출력 디렉터리(또는 worktree). Agent 백그라운드 + Codex CLI |
| 판정 | **기계 채점** — lint 30 / tests 40 / diff_size 15 / files_scope 15 가중합, 실격 규칙, 동점은 짧은 diff | **과제별 기준표(3~6개)** + 교차 판정자 1명 + 리드가 전부 읽고 기준별 채점 |
| 결과 | **승자 독식** — 승자 브랜치 cherry-pick/머지, 패자 worktree 는 `/tmp/harness-race-losers/` 격리 | **바탕 + 접붙이기** — 바탕 하나에 탈락 후보의 좋은 점 1~2개씩을 손으로 옮겨 합침 |
| 동시성 | RACE_MODE 최대 1개, 기본 provider 2개(claude+codex) | 후보 2~3개, Agent 동시 3개 이하 |
| 기록 | registry `result.winner`, `result.scores`, `.claude/race-artifacts/<ISS>/` | 합성 메모(바탕·이유·접붙인 것·버린 것·탈락) |

고르는 법:
- 테스트·lint 로 좋고 나쁨이 갈리는 **구현**이고 하나만 남기면 되면 → RACE_MODE.
- 좋고 나쁨이 **판단**이고(설계 모양, 글, 구조) 후보마다 다른 장점을 합치고 싶으면 → arena.
- 산출물 없이 커버리지·측정·탐색 결과만 모으면 → `swarm`.

## 시작

할 일 목록에 단계별 항목을 연다: 틀, 펼치기, 교차 판정, 바탕 고르기, 접붙이기, 검증.

## A. 틀

모든 후보가 같은 프롬프트를 받으므로 프롬프트가 계약이다.

1. 후보 각각이 만들 산출물을 적는다.
2. **기준표** — 이 과제에서 성공이 뭔지 채점 가능한 구체 기준 3~6개. D 에서 리드가 쓰는 도구다. 후보에게는 과제만 준다.
3. **후보 구성** (원본의 모델 시트·provider-dispatch 대신):
   - Claude 후보: `Agent`(`general-purpose`), 부모 모델, `run_in_background`.
   - Codex 후보: `codex e --skip-git-repo-check -s workspace-write -C <후보 전용 디렉터리> "<과제 + 근거 경로 + 출력 경로>" < /dev/null` (Bash `run_in_background`). 로그인 확인 `codex login status`.
   - 설계 방향이 여럿이면 후보를 늘리되 동시 3개 이하. 판단보다 생성량이 중요한 과제면 같은 모델을 N번 띄워도 된다.
4. 후보마다 전용 출력 위치: `<scratchpad>/arena-<slug>/candidate-<n>/`. 저장소 안에서 쓰게 하지 않는다(저장소당 Codex 1개 규칙, 공유 상태 분리).

## B. 펼치기

모든 후보를 한 번에 띄운다(백그라운드, 포그라운드 장시간 실행 금지). 각 후보에게 과제, 공용 근거 자료 경로, 자기 출력 경로, 그리고 "산출물 + 검토했다가 버린 대안을 적은 짧은 근거"를 만들라는 지시를 준다.

후보는 실제로 결과 파일을 남겼을 때만 센다. 실패하면 N-1 로 진행하고 합성 메모에 탈락을 정확히 적는다. 다른 모델로 몰래 대체하지 않는다. 시크릿이 든 자료는 Codex 에 보내지 않는다.

## C. 교차 판정

B 가 모두 끝난 뒤, 부모 및 바탕이 될 것 같은 후보와 **다른 모델**로 읽기 전용 판정자 1명을 띄운다(보통 Codex `codex exec -s read-only ... -o <출력>`, Codex 가 후보였으면 별도 Claude Agent). 판정자는 기준표와 후보(경로 이름표로만)를 보고 기준별 점수와 추천 바탕을 낸다. D 에서 내가 읽는 동안 병렬로 돈다. 후보가 아직 쓰는 중에는 띄우지 않는다.

## D. 바탕 고르기

고르기 전에 모든 후보를 처음부터 끝까지 읽는다. 전체 느낌이 아니라 기준별로 채점하고 판정자와 비교한다. 바탕이 일치하면 확정, 다르면 둘 중 하나가 편향됐거나 기준표가 모호했다는 뜻이니 양쪽 근거를 다 읽고 정한다.

미래 유지보수자가 불변식을 깨지 않고 가장 쉽게 확장할 후보를 바탕으로 한다. 비슷하면 경계가 깔끔하거나 API 가 작은 쪽.

## E. 접붙이기

탈락 후보를 한 번 더 훑어 바탕에 옮길 가치가 있는 것을 고른다. 보통 후보당 1~2개, 대부분이 아니다. 기계적으로 붙여 넣지 말고 하나의 머릿속 모델로 일관되게 다시 쓴다.

- 산출물이 문서·설계면 내가 합친다.
- 산출물이 **저장소 코드**면 합치기는 Codex 에 위임한다: `codex e --skip-git-repo-check -s workspace-write "<정확한 파일 경로 + 바탕 후보 경로 + 접붙일 항목 목록>" < /dev/null` → `git diff` 검수 → 직접 실행 검증 → 결함은 Codex 재위임. 상세: `opus-codes`.

후보들이 한 모양으로 수렴하면 강한 합의다. 적어 두고 그 모양을 그대로 쓴다(접붙이기 불필요). 크게 갈리면 A 가 덜 정해졌다는 뜻이다. 평균 내지 말고 틀을 다시 잡아 다시 돌린다.

## F. 검증

합쳐진 산출물을 다른 결과물처럼 검증한다(prove-it-works). arena 가 놓친 문제가 검증에서 나오면 A 가 틀렸거나(다시 틀 잡고 재실행), 어느 후보가 잡았는데 내가 접붙이기를 놓친 것이다(E 로). 덮지 않는다. 이슈 완료 근거는 on_complete result 의 `proof[{cmd,exit_code,output}]`.

## 산출물 (한국어)

합쳐진 산출물 하나 + 짧은 합성 메모: 바탕과 이유, 교차 판정 결과, 접붙인 항목과 출처 후보, 버린 것과 이유, 수렴·탈락, 검증 결과.
