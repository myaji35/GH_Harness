# 검증 스킬 만들기

> 출처: open-pstack `create-verification-skill` (MIT, NOTICE.md). GH_Harness 규칙에 맞게 옮김.

목적: 다음 에이전트가 처음 보는 앱을 **실제로 띄우고, 사용자처럼 조작하고, 증거를 남길 수 있게** 하는 프로젝트 전용 스킬을 만든다. 읽는 사람은 대표님이 아니라 작업 중간에 이 스킬을 처음 여는 에이전트다.

하네스 연결:
- 생성 위치: 프로젝트 `.claude/skills/verify-<app>/`
- 이 스킬로 얻은 실행 결과가 on_complete 의 `"proof":[{"cmd","exit_code","output"}]` 가 된다.
- "완료의 정의" 2단계 `payload.user_test_passed_at` 은 이 스킬의 여정(journey)을 돌린 결과로만 찍는다.

## 1. 대표님이 아니라 저장소에 묻는다

코드에서 답을 찾고, 관찰할 수 없는 것만 묻는다.

- **표면**: 사용자가 실제로 만지는 것(웹 UI·CLI·데스크톱·API·모바일·라이브러리). 여러 개면 주력 하나를 고르고 나머지는 적어 둔다.
- **실행**: 로컬 기동 방법. 저장소에 문서화된 명령(package scripts·Makefile·README·`run-server` 스킬 포트 규칙)을 우선. 포트·환경변수·시드 데이터·인증을 적는다.
- **조작**: 기존 하네스부터(Playwright/Cypress 스펙, gstack browse, curl 가능한 엔드포인트). 없으면 일반 레시피 — 웹은 browser/CDP, CLI/TUI 는 tmux/PTY, 서비스는 HTTP.
- **관찰**: 남길 수 있는 증거(스크린샷·터미널 기록·응답 본문·로그·exit code·DB 상태).
- **격리**: 두 인스턴스를 나란히 띄울 수 있는가(포트·데이터 디렉터리·프로필). 안 되면 생성 스킬에 명시한다 — 대표님이 쓰는 인스턴스를 같이 조작하는 것보다 거부하는 게 낫다.

체크아웃이 그대로 빌드·기동되지 않으면 먼저 고치거나 정확히 보고한다. 깨진 기반 위에 쓴 스킬은 틀린 절차를 가르친다. 무관한 누락 자산(서빙하지 않는 static 디렉터리, 샘플 설정)이 기동을 막으면 "검증용 임시 자산"으로 표시해 만들고 Cleanup 에서 지운다.

## 2. 스킬 생성

`.claude/skills/verify-<app>/SKILL.md` 를 YAML frontmatter(`name: verify-<app>`, 앱·표면·언제 쓰는지를 담은 `description` — frontmatter 가 없으면 스킬이 등록되지 않는다)와 아래 절로 쓴다. 각 절은 조사에서 실제로 찾은 것으로 채운다(placeholder 금지).

- **Launch**: 검증용 기동 명령과 준비 완료 판정(로그 줄·프롬프트). 빈 데이터 디렉터리에서 마이그레이션·시드까지 포함해 "쓸 수 있는 상태"에 도달해야 한다. 프로세스가 응답하는 것과 쓸 수 있는 것은 다르다(DB 헬스체크는 init 스크립트가 도는 중에도 통과한다). 종료 방법 포함. 짧게 끝나는 CLI 는 서버가 없으니 바이너리 빌드(또는 의존성 설치) 1회 후 매 조작을 별도 PTY/tmux 세션에서 시작한다.
- **Doctor**: "이 인스턴스를 조작해도 되나?"에 답하는 읽기 전용 점검 1개 — 프로세스 생존, 올바른 버전/빌드, 포트 소유가 우리인지, 인증 유효. 뭔가 이상하면 이것부터 돌린다.
- **Drive**: 이 저장소의 실제 셀렉터/명령으로 쓴 조작 레시피. 좌표·탭 순서보다 안정적인 손잡이(ARIA 라벨·data 속성·프롬프트 문자열·라우트 경로)를 쓴다.
- **Evidence**: 증거로 무엇을 어디에 남기는지. 증명 기준:
  - 내부 setter·테스트 전용 엔드포인트가 아닌 **실제 사용자 경로**를 탄다.
  - 최종 화면만이 아니라 **행동과 그 결과 상태**를 남긴다.
  - 보이는 것과 함께 **부수효과**(파일 생성·행 삽입·메시지 발송)를 확인한다.
  - mock 은 운영에서도 외부 시스템이 격리되는 경계에서만.
  - dry-run/test 모드가 안전 경로라면 이름을 믿지 말고 실제로 무엇을 건너뛰는지 관찰한다(파일·네트워크·git ref). 어떤 dry-run 은 네트워크를 타거나 브라우저를 연다.
  - 출력 형식은 하네스 proof 와 맞춘다: 실행한 명령, exit code, 실제 출력(또는 증거 파일 경로).
- **Cleanup**: 이번 실행이 띄운 것만 내린다. 프로세스 이름으로 죽이지 않는다 — 내가 띄운 PID 만. 증거는 지우지 않는다. 증거 보관 위치를 스킬에 명시한다.
- **Helpers**: 스킬이 포함하는 스크립트는 실행 권한이 있고 호출법이 본문에 있다. 역분석해야 쓸 수 있는 헬퍼는 헬퍼가 아니다.

외부 영향(실제 결제·메일 발송·운영 DB 쓰기·외부 게시)이 있는 기능은 Drive 에 "T2 — 운영 대상 금지, 테스트 계정/샌드박스로만"을 명시한다.

## 3. 기능 지도(feature map) 시드

`.claude/skills/verify-<app>/features/README.md`(색인) + 사용자 기능 1개당 파일 1개. 라우트·명령·메뉴·문서에서 상위 3~5개로 시작한다. 형태는 [`references/feature-map-example/`](references/feature-map-example/) 를 따른다.

각 파일의 H2 4개: `Sub-features`, `How to get to it (user POV)`, `Driving it with <harness>`, `Gotchas`. 사용자 관점으로 기능이 무엇인지, 어떻게 도달하는지, 하네스로 어떻게 조작하는지, 무엇이 관찰되면 동작이 증명되는지를 쓴다.

시드 데이터에 여정의 전제조건이 없으면 여정은 실패를 보고하고 이유를 그 기능의 `Gotchas` 에 적는다. **통과시키려고 여정을 약하게 만들지 않는다.** 지도에 진입점이 여러 개 있는데 편한 하나만 돌린 증명은 미완이다.

## 4. 넘기기 전에 생성한 스킬을 실제로 돌린다

생성한 스킬의 지시대로 처음부터 끝까지 1회: Launch → Doctor → 지도의 기능 **1개** 조작 → 증거 → Cleanup. Cleanup 후 증거가 명시한 위치에 남아 있는지 확인한다(증거를 지우는 Cleanup 은 실패). 실패하면 고치고, 실패한 시도마다 Cleanup 도 돌려 프로세스·포트를 남기지 않는다.

한 번도 실행되지 않은 생성 스킬은 초안이지 산출물이 아니다. 실제 대상 대신 대역(컨테이너 대신 로컬 등)에서 증명했다면, 실제 대상에서는 하지 않을 준비 단계를 모두 나열한다 — 그 단계는 실제 대상에서 돌릴 때까지 미검증이다.

이 1회 실행 기록이 이 작업 이슈의 `proof` 다.

## 5. 유지 루프 안내

앱이 바뀌면 지도가 썩는다. 유지는 `maintain-verification-skill` 스킬로 한다고 보고에 한 줄 남긴다. 주기는 대표님이 물을 때만 제안한다.
