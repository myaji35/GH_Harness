# Recall (작업 맥락 복원)

> 출처: open-pstack `recall` (MIT, NOTICE.md). GH_Harness 규칙에 맞게 옮김.

**작업을 시작·재개하기 전에 최근 작업 맥락을 다시 세우고, 지금 상태와 다음 행동을 담은 짧은 캡슐을 돌려준다.**

짧게, 주제에 맞게. 범위 안의 흐름에 필요한 것만 읽고 멈춘다.

맥락은 두 기록에 있다.
- **내 대화 기록**: 내가 한 일과 결정. `~/.claude/projects/<encoded-cwd>/<uuid>.jsonl` (워크스페이스 경로의 `/` 와 `.` 를 모두 `-` 로 바꾼 이름. 예: `/Volumes/GH_APFS/0000_master` → `-Volumes-GH-APFS-0000-master`). 한 줄이 메시지 하나.
- **공유 기록**(하네스): 같은 코드 주변에서 다른 이름으로 일어난 일 — 반복 보고된 증상, 들어갔다가 되돌려진 수정, 이전 결정. 하네스에서는 아래가 공유 기록이다.

| 공유 기록 | 조회 방법 | 담긴 것 |
|---|---|---|
| 세컨드브레인 | `python3 -I /Volumes/GH_APFS/0000_master/scripts/brain/recall.py "<질의>" --project <폴더명>` | 프로젝트 기억 사본, `대표님-답변/`(이전 결정·값·용어) |
| 이슈 DB | `.claude/issue-db/registry.json` (title·status·payload·result) | 대표님 지시, 진행·실패·되돌림, proof |
| 세션 복원 | `bash .claude/hooks/session-resume.sh` | IN_PROGRESS·READY 이슈, 중단 지점 |
| 하네스 지식 | `.claude/knowledge-db/`, `.claude/trace/*.jsonl`(decision-trace), `docs/incident-*.md` | 실패 패턴, 이슈 생애 이벤트, 사고 |
| 소스 이력 | `git log`, `gh pr list/view` | 실제로 들어간 것 |

기능에 긴 버그 꼬리가 있으면 이야기 대부분이 공유 기록에 있다. 내 대화 기록만으로 재구성하지 않는다.

## 절차

1. **분류 후 경로 선택.**
   - 이전 대화 **하나**를 이어받는 것이면 그 transcript 를 직접 읽는다(아래 팬아웃 불필요).
   - 습관을 오래 가는 규칙·스킬로 만드는 것이면 `update-claudemd` 또는 `anthropic-skills:skill-creator`.
   - 사람이 읽을 업무 보고는 `what-did-i-get-done`.
   - 대표님이 이미 상태 캡슐(경로·브랜치·변경)을 주셨으면 그걸 쓰고 채굴을 건너뛴다.
2. **검색 전에 범위를 고정한다.** 기간("최근" = 기본 최근 7일), 주제(있으면), 워크스페이스(기본 현재 것. **요청 없이 다른 프로젝트 transcript 를 읽지 않는다**). 범위를 한 줄로 밝힌다(묻지 않는다 — 대표님이 바꿀 수 있다). "전부"를 몰래 "최근 N개"로 줄이지 않는다.
3. **대화 기록 팬아웃.** 대화가 1~2개면 직접 찾는다. 많으면 `Agent`(`subagent_type: Explore`, `model: haiku` 또는 `sonnet`) 를 조각별로 **한 번에 동시에** 띄운다(동시 3개 상한). 서브에이전트 지시:
   - 후보는 실제 수정 시간 순(`ls -t`), UUID 이름 순 금지.
   - 주제로 먼저 grep 하고, 맞는 대화의 관련 구간만 읽는다.
   - 현재 대화와 잡음(서브에이전트·평가·테스트 대화)은 건너뛴다.
   - 대화마다 같은 형식으로 반환: 주제 / 대표님 목표 / 결정 / 열린 흐름 / 막힘·교정 / 산출물(PR·이슈·브랜치), 각각 대화 UUID 인용.
   - 원본 transcript 는 서브에이전트 안에 둔다. 메인 스레드는 결과만 받는다.
4. **공유 기록 훑기.** 주제가 기능·파일·서브시스템·영역·버그를 지목하면 **기본으로 한다**("내 작업" 이라는 말도 면제가 아니다). 3번과 병렬로:
   - 세컨드브레인 `recall.py` 를 주제어로 실행한다.
   - registry.json 에서 주제 관련 이슈(title·payload 검색)의 status·result·되돌림 여부를 뽑는다. `session-resume.sh` 로 진행 중 이슈를 확인한다.
   - 이력이 깊으면 `why` 스킬의 조사 범주(소스 이력·이슈 DB·하네스 지식·장기 문서)를 빌려 쓰되 질문을 "왜 이렇게 만들었나"에서 **"지금 상태는? 무엇을 시도했다 안 됐나? 대표님·사용자가 계속 보고하는 것은?"** 으로 바꾼다.
   - 빈 결과도 발견이다. 못 쓰는 출처는 건너뛰고 그렇다고 적는다.
   - 대상 없는 순수 활동 회상("이번 주 뭐 했지")이면 이 단계를 건너뛴다.
5. **실상태 검증.** 드러난 PR·브랜치·이슈를 `git`·`gh`·registry 로 확인한다. 에이전트가 실제로 무엇을 했는지(실행한 도구·읽은 파일·만난 에러)가 답을 가르면 잘린 사본이 아니라 전체 transcript 를 읽는다.
6. 아래 형식으로 브리핑을 쓴다. 흐름별로 묶고 주제에 머문다.

## 출력 형식 (한국어)

캡슐 → 흐름 상태 → 문제 → 다음 행동 순. 더 깊은 내용은 아래로 내리거나 잘라낸다.

- **캡슐.** 최대 5줄. 이 작업이 무엇이고 전체적으로 어디까지 왔나.
- **흐름.** 한 줄씩, 상태 태그 정확히 하나: `[병합 #N]`, `[열린 PR #N]`, `[진행 중 <브랜치>]`, `[검증됨, 미커밋]`, `[되돌림 #N]`, `[계획만, 미착수]`, `[이슈 ISS-NNN <status>]`. 태그 없는 흐름은 끝나지 않은 것이니 태그를 붙인다.
- **문제.** 최대 5개, 반복되는 것. 계속 보고되는 증상과 들어갔다 되돌려진 수정을 넣어 다음 시도가 지난 실패 지점에서 시작하게 한다.
- **다음 행동.** 가장 쓸모 있는 다음 행동 하나, 구체적으로. 지시 범위 안의 T0 일이면 브리핑 뒤 바로 착수해도 된다(하네스 자율 실행 원칙). 단 이전 세션의 READY 이슈는 대표님 재지시가 있어야 착수한다.

인접 기능·이슈는 이 작업을 막을 때만 넣는다. 화면을 넘치면 흐름이 아니라 세부를 먼저 자른다. 대화 결과는 UUID 로, 공유 기록 결과는 출처(PR #, ISS-NNN, 볼트 노트 경로, 커밋)로 인용한다. 시크릿 값은 쓰지 않는다(위치만). 외부에 내보낼 출력에서는 사적 맥락을 지운다.
