# Figure it out (절차 설계 후 실행)

> 출처: open-pstack `figure-it-out` (MIT, NOTICE.md). GH_Harness 규칙에 맞게 옮김.

맞는 스킬이 없으면 절차부터 만든다. 코드보다 먼저 나오는 산출물은 **작업 절차 자체**다 — 작업 크기에 맞춰 엄밀도를 정한 단계 목록, 가설-검증 루프, 대표님이 돌아와서 감사할 수 있는 결정 기록.

먼저 하네스에 맞는 경로가 있는지 본다: 기능 추가는 FEATURE_PLAN, 버그·리팩토링은 FIX_BUG/REFACTOR, 설계 결정은 `architect`. 그래도 맞는 게 없을 때 이 스킬을 쓴다.

## 시작

할 일 목록(TaskCreate 또는 이슈 `payload.steps`)을 열고 아래 단계를 항목으로 넣는다. 원칙 참고: `pstack-principles` 스킬(이식돼 있으면)의 prove-it-works, foundational-thinking, sequence-verifiable-units, encode-lessons-in-structure.

## A. 틀 잡기

먼저 근거를 모으고(`how` 스킬로 관련 서브시스템 파악) 아래를 말할 수 있을 때 시작한다.

- **완료의 정의** — 반증 가능한 판정식. "X 명령이 Y 를 출력한다", "페이지 Z 가 200 을 반환하고 버튼이 보인다" 수준.
- **범위의 양** — 대략 단위 수·노력, 조사 중 드러난 막힘.
- **엄밀도** — 높게 잡는다. 되돌릴 수 없는 결정·영향 반경 큰 변경은 더, 되돌릴 수 있는 저위험 단계는 덜. 엄밀도는 "더 열심히"가 아니라 게이트와 산출물이다.

틀과 트레이드오프는 한 단락으로 보고만 하고 진행한다(되돌릴 수 있으면 묻지 않는다 — T0). 몇 시간짜리 장기 실행이면 시작 전에 한 번 현황을 알린다. 외부 배포·삭제·보안·예산(T2)이 끼면 그 단계만 `request-user-confirm.sh` 로 멈춘다.

## B. 절차 설계

- 독립적으로 반영 가능한 원자 단위로 쪼갠다. **가장 위험한 미지수부터** 배치한다. 뼈대·검증 장치가 기능보다 먼저다.
- 검증 장치를 작업 전에 만들고 **변경 전 기준값**을 잡아 둔다. 확인은 "이전 값 vs 새 값"으로 읽힌다. 프로젝트에 검증 경로가 없으면 `create-verification-skill`.
- 되돌릴 수 없는 설계 결정에는 `architect`(내부에서 `arena`)를 쓴다. 모양이 이미 정해진 기계적 작업에는 쓰지 않는다. 정해진 설계에 arena 를 또 돌리는 건 과잉이다.
- 병렬로 펼칠 것을 정한다. 경계(seam)가 분명한 곳만, 작업자마다 자기 worktree 나 출력 경로를 준다. 읽기·조사 병렬은 `swarm`(Agent 동시 3개 이하). 과하게 펼치지 않는다.
- 설계한 단계 목록을 적어 둔다. 대표님이 검토하는 대상이 이 목록이다.

설계한 단계를 C 와 D 사이 항목으로 할 일 목록에 넣고, 각 단계를 C 의 루프로 돌리며 D 의 기록을 단계마다 한 줄씩 쌓는다(끝에 몰아 쓰지 않는다).

## C. 루프 실행

단위 하나가 실험 하나다. 가설을 말하고 → 가장 작은 변경 → 실제 산출물에서 판정식으로 측정 → 진전이면 유지, 아니면 되돌린다. 다음 단위 전에 지금 단위를 검증한다(끝에 몰아서 확인하지 않는다).

- **코드 변경은 Codex 에 위임한다.** `codex e --skip-git-repo-check -s workspace-write "<정확한 파일 경로 + 구체 변경 지시>" < /dev/null` → `git diff` 로 검수(정확성·범위·회귀·규칙 위반·과잉 변경) → 내가 직접 실행해 검증 → 결함은 직접 고치지 않고 구체 지시로 Codex 재위임. 같은 저장소에서 Codex 는 한 번에 하나. 상세: `opus-codes` 스킬.
- 검증은 자기 신고가 아니라 산출물을 직접 보고 한다. Codex 의 "완료" 보고는 근거가 아니다. 너무 쉽게 통과하면 시스템보다 관찰 방법을 먼저 의심한다.
- 위임한 일에는 판정자를 붙인다. 작업자가 게이트를 꼼수로 넘으면 계약을 단단히 해서 다시 시킨다. 게이트 자체가 틀렸으면 우회하지 말고 게이트를 별도 변경으로 고친다.
- 판정은 **검증됨 / 검증 안 됨 / 판단 불가** 셋 중 하나. 판단 불가는 통과가 아니다. 부정적 결과를 숨기지 않는다.

## D. 결정 기록

결정마다 무엇을·왜·근거 명령을 남긴다. `show-me-your-work` 스킬이 있으면 그 형식, 없으면 `.claude/hooks/decision-trace.sh` 기록 또는 이슈 `result.decisions` 에 남긴다. 장기 작업이면 기록 파일을 커밋해 diff 와 함께 읽히게 한다.

## E. 검증 후 인계

전체를 A 의 판정식으로 **실제 제품에서** 확인한다(검증 장치만이 아니라). 반복된 교정은 문장이 아니라 게이트·lint·체크·스크립트 이슈로 남긴다(encode-lessons-in-structure — 코드 변경이면 Codex 위임).

완료 증거는 prove-it-works 형식으로 on_complete 에 넣는다:

```bash
bash .claude/hooks/on_complete.sh ISS-NNN <type> '{"proof":[{"cmd":"<실행한 명령>","exit_code":0,"output":"<실제 출력>"}]}'
```
