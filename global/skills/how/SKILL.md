# How

> 출처: open-pstack `how` (MIT, NOTICE.md). GH_Harness 규칙에 맞게 옮김.

코드베이스를 탐색해 "X는 어떻게 동작하나"에 답한다. 수준은 서브시스템에 새로 투입된 시니어 엔지니어에게 하는 설명 — 일할 수 있는 머릿속 모델이 생길 만큼, 주석 달린 소스처럼 읽히지 않을 만큼. 모든 탐색은 **읽기 전용**이다.

## 1. 복잡도 판단

범위가 모호하면 해석을 한 줄로 밝히고 탐색한다. 대표님이 방향을 바꿀 수 있다.

- **단순**(모듈 하나, 작은 유틸, "함수 X는 어떻게 동작해" 같은 좁은 질문): 서브에이전트 없이 **직접** 읽고 `references/explainer-prompt.md` 의 출력 형식으로 바로 설명한다. 4로.
- **복잡**(여러 파일·서비스에 걸친 서브시스템, 횡단 기능, 전체 구조 개관): 2로.

애매하면 단순 경로. (하네스 위임 정책: 몇 번의 도구 호출로 끝날 일은 직접 한다.)

## 2. 탐색 (복잡할 때만)

질문을 서로 다른 단면 2~3개로 나눈다. 단면마다 `Explore` 서브에이전트 1개를 `references/explorer-prompt.md` 에 단면을 채워 **한 번에 동시에** 띄운다(동시 3개 상한).

## 3. 종합 (복잡할 때만)

탐색 결과가 다 오면 직접(서브에이전트 없이) `references/explainer-prompt.md` 를 따라 종합한다. 겹치는 설명은 합치고, 모순은 코드를 직접 확인해 해소한다.

## 4. 제시

`explainer-prompt.md` 의 절을 쓰되 해당 없는 절은 뺀다: 개요 / 핵심 개념 / 동작 방식 / 어디에 있나 / 함정. **한국어로**, 파일은 `path:line` 으로 인용한다(클릭 가능). 흐름에 구성요소가 셋 이상 오가면 mermaid 또는 ASCII 다이어그램을 넣는다 — 장식이 아니라 이해를 돕는 경우만.

대표님이 비개발자 관점으로 묻는 경우(용어를 모르는 티가 나면) 용어를 처음 쓸 때 한 줄 풀이를 붙인다. 더 쉽게 이해시키는 게 목적이면 `teach` 스킬로 넘긴다.
