# 검증 스킬 유지

> 출처: open-pstack `maintain-verification-skill` (MIT, NOTICE.md). GH_Harness 규칙에 맞게 옮김.

`create-verification-skill` 로 만든(또는 기능 지도가 있는 아무) 프로젝트 검증 스킬의 유지 루프다. 엄밀함의 단위는 문장이 아니라 **기능**이다 — 모든 기능 파일을 소스로 확인하고, 모든 기능을 라이브로 조작한다.

## 결과는 셋 중 하나 (보고에 명시)

- **clean** — 모든 기능이 소스·라이브 확인됨. 보정할 것 없음. 커밋 없음.
- **changed** — 증명된 문서·하네스·지도 보정을 **커밋 1건**으로 남김.
- **blocked** — 확인을 끝내지 못했거나 증명된 보정을 안전하게 반영 못 함. 무엇이 막았는지 정확히.

## 편집 범위

검증 스킬 자기 디렉터리(SKILL.md, features/, 소유한 하네스 스크립트)만 고친다. **제품 코드는 고치지 않는다.** 지도에 적힌 동작을 앱이 더 이상 안 하면 둘 중 하나다:
- 문서 표류(doc drift) → 지도를 고친다.
- 제품 회귀(regression) → 문서로 덮지 말고 `FIX_BUG` 이슈로 등록·보고한다.

## 절차

0. **대상 찾기.** 실행·조작 절과 기능 지도가 있는 프로젝트 스킬(보통 `.claude/skills/verify-*/`). 후보가 여럿이면 기능 지도가 가장 최근에 바뀐 것을 고르고 보고에 적는다. 없으면 멈추고 `create-verification-skill` 을 쓰라고 보고한다 — 대상을 지어내지 않는다.

1. **색인 정리.** 지도 README 와 형제 파일을 대조해 누락·잉여·중복·죽은 항목을 고친다. 가볍게.

2. **소스 확인.** 기능 파일마다 "이 사용자 기능은 소스상 어떻게 동작하나?"를 확인하고, 표류 의심은 인용(file:line)과 함께 적고, 라이브 검증 레시피 1개를 뽑는다. 앱을 조작하거나 파일을 고치지 않는다.
   - 위임 정책: 기능이 5개 이하이면 직접 읽는다. 6개 이상이고 서로 독립적이면 읽기 전용 Explore 서브에이전트로 나눈다(동시 3개 상한, `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`). 반환 형태: 기능 요약 / 소스 진입점 / 표류 의심 또는 없음 / 레시피 1개.

3. **대조.** 모든 기능 파일에 요약이 있는지 확인. 겹치는 레시피는 가능한 적은 앱 상태로 합친다. 인용된 표류는 표본 확인, 깨끗한 주장은 다시 증명하지 않는다. 최근 변경(git log)에서 지도에 없는 사용자 표면을 찾되, 구체적 소스 경로가 있어야 "누락"이라 부른다.

4. **라이브 패스.** 소스가 깨끗해 보여도 **필수**. 조작은 전부 직접(코디네이터) 한다. 기동 모델은 검증 스킬의 Launch 절을 따른다(서버·UI 는 장수 인스턴스 1개를 직렬로, 짧은 CLI 는 조작마다 새 격리 세션). 모든 기능을 최소 1회 조작하며 아래 3불변식을 끝까지 지킨다:
   1. 마지막으로 이상한 일을 한 뒤 Doctor 로 확인하지 않은 인스턴스는 조작하지 않는다 — 첫 조작 전, 세션 단위면 세션마다, 실패한 조작 직후 Doctor. Doctor 가 못 보는 실패(프로세스는 멀쩡한데 UI 가 굳음)면 기대지 말고 알려진 상태로 리셋하거나 재기동.
   2. 지금까지의 증거는 어떤 Cleanup 뒤에도 명시 위치에 남아 있다 — 가정하지 말고 확인.
   3. 조작이 띄운 것은 쓸모가 끝나면 남기지 않는다 — 세션이 굳었든 끝났든 공유든 실패 잔여물은 정리(공유 인스턴스면 잔여물만, 인스턴스는 그대로).
   - 스킬 표류 때문에 Doctor 가 실패하면 그것도 표류다. 편집 범위 안에서 고치고 1회 재시도(무효화된 것만 재기동) 후 그래도 안 되면 `blocked`.
   - 도달 불가 기능은 구체적 전제조건(인증·권한·OS·외부 상태)과 시도한 경로가 있을 때만 `verified-unreachable`. 지도에 그 전제조건이 없으면 그것도 표류.
   - 분류에서 나온 하네스 수정은 반영 전에 라이브로 다시 조작한다. 최종 종료는 마지막 조작(재증명 포함) 뒤에 — 증거는 남긴다.

5. **분류.** 사용자 관점 설명이 틀림/누락 → 문서 표류, 고친다. 동작은 하는데 하네스가 못 조작 → 하네스 갭, 고친다(헬퍼 규칙 동일: 실행 권한 + 본문에 호출법). 앱이 실제로 고장 → 제품 갭, `FIX_BUG` 이슈로 등록하고 이 커밋에서 뺀다.

6. **반영 또는 중단.** changed: 바뀐 파일을 다시 읽은 뒤 커밋 1건(secret-guard 통과). clean/blocked: 커밋 없이 결과와 커버리지를 정직하게 보고.

실행 메모(확인한 기능, 도달 불가 전제조건, 확인된 표류, 결과)는 스크래치 위치에 짧게 두고 커밋하지 않는다. 이 작업 이슈의 `proof` 에는 라이브 패스에서 실제 실행한 명령·exit code·출력을 넣는다.
