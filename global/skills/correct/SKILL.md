# Correct (반복 실수를 구조로 막기)

> 출처: open-pstack `correct` (MIT, NOTICE.md). GH_Harness 규칙에 맞게 옮김.

대표님이 이 저장소에서 같은 실수로 에이전트를 계속 교정한다. 다음 에이전트가 그 실수를 **할 수 없게** 저장소를 바꾼다.

**meta-evolution 과의 구분:** meta-evolution(meta-agent)은 이슈 결과를 주기적으로 관찰해 패턴을 찾고 **개선 이슈를 만드는** 감시자이고, correct 는 대표님 교정이 왔을 때 그 실수 부류를 **lint·hook·타입·테스트로 지금 막는** 실행자다.

이 스킬은 대표님이 부를 때(또는 교정을 받았을 때)만 쓴다.

모든 기여자가 에이전트라고 가정한다 — 연 파일만 보고, 가장 가까운 예시를 베끼고, 컴파일되는 가장 짧은 길을 택한다. 한 파일에서 맞아 보이는 변경이 저장소 전체에서 맞도록 설계한다.

## 실수 부류 찾기

먼저 읽는다: 최근 커밋·되돌림(`git log`, `git log --grep=revert -i`), 리뷰 코멘트(`gh pr view --comments`), 에이전트 지시 파일(CLAUDE.md, `.claude/CLAUDE.md`, 메모리 `~/.claude/projects/*/memory/`), 우회책을 설명하는 주석. 하네스에서는 추가로:
- `.claude/issue-db/registry.json` 의 FAILED·되돌아온(reopened) 이슈, on_complete 가 proof 부족으로 거부한 기록
- `.claude/knowledge-db/failure_patterns.json`, meta-review 가 만든 SYSTEMIC_ISSUE·PATTERN_ANALYSIS 이슈
- CLAUDE.md 의 "근거: <사고>" 줄과 `docs/incident-*.md`
- 세컨드브레인 `대표님-답변/`(`python3 -I /Volumes/GH_APFS/0000_master/scripts/brain/recall.py "<실수 키워드>" --project <폴더명>`)

실수를 부류로 묶는다. **두 번 일어나야** 부류로 친다.

## 부류마다 통하는 가장 높은 단계에서 막기

1. **아키텍처로 없앤다.** 상태마다 주인 하나, 작업마다 지원되는 방법 하나. 내부를 숨겨 잘못된 import 가 실패하게 한다. 손으로 맞추는 목록을 단일 진실 소스로 바꾼다. 에이전트가 베낄 옛 방식·죽은 코드를 지운다(핵심 기능 삭제면 T2 DIRECTION).
2. **타입으로 나쁜 상태를 쓸 수 없게 한다.** 그래도 나쁜 코드가 컴파일되면, 오류 메시지가 **대신 쓸 파일·타입·함수 이름**을 대는 lint 또는 검사를 더한다. 패턴이 이미 흔하면 변경이 더 늘릴 때만 실패하게 한다. 하네스에서는 PreToolUse/PostToolUse hook(secret-guard·freeze-guard 같은 방식)과 on_complete 게이트도 이 단계의 도구다.
3. **동작을 테스트한다.** 검사하는 동작이 깨져도 통과하는 테스트, 내부만 바뀌어도 실패하는 테스트는 고치거나 지운다.
4. **문서·에이전트 규칙은 마지막, 판단이 필요한 것에만.** 에이전트가 건너뛰어도 아무것도 실패하지 않는다.

## 고치고 증명하기 — Codex 위임

가장 자주 나는 부류부터 **지금** 고친다. 부류 하나당 변경 하나.

1. **위임 전 검수**: 부류 진단이 실제 코드와 맞는지 확인한다(그 실수가 실제 두 번 있었는가, 막을 지점이 맞는가).
2. **Codex 에 위임** — 코드·hook·lint 설정·테스트는 줄 수와 무관하게 Codex 가 쓴다:
   ```bash
   codex e --skip-git-repo-check -s workspace-write "<정확한 파일 경로> 에 <검사 내용>을 추가하라. 오류 메시지는 '<대신 쓸 것>'을 이름으로 대야 한다. <과거 실수 커밋/파일>에 대해 실패해야 한다. 다른 파일은 건드리지 마라." < /dev/null
   ```
3. **위임 후 검수**: `git diff` 로 정확성·범위·회귀·과잉 변경을 본다. 결함은 직접 고치지 않고 Codex 에 구체적 수정 지시로 재위임한다.
4. **직접 증명**: 새 검사가 **실제 과거 실수에서 실패**하고 현재 코드에서는 통과함을 내가 실행해 보인다(예: 과거 커밋을 임시 worktree 로 꺼내 검사 실행). 결과는 `proof[{cmd, exit_code, output}]` 로 남긴다. 로컬과 CI 에서 같은 명령을 쓴다(CI 가 없는 프로젝트는 hook·on_complete 에서 같은 명령).
5. **커밋**: 검증 후 부류 하나당 커밋 하나(하네스 커밋 규칙·secret-guard 통과). 이슈로 진행 중이면 `on_complete.sh` 에 proof 를 넣는다.

**예외**: 위반 줄에 사유·만료일을 단 주석으로만 허용한다. 원본은 "사람의 승인"을 요구하지만, 하네스에서는 예외마다 묻지 않는다(되돌릴 수 있는 일이라 T0). 예외는 사유·만료일과 함께 최종 답변의 "예외 목록"에 모아 보고하고, 대표님이 보고를 보고 뺄 수 있게 한다. 보안·외부 배포에 걸린 예외만 T2(`request-user-confirm.sh`).

## 규칙 표 유지

마지막으로 에이전트 지시 파일(프로젝트 `CLAUDE.md`)에 **규칙 ↔ 강제 장치** 표를 둔다(문서 수정은 내가 직접 한다).

| 규칙 | 강제 장치 | 근거(과거 실수) |
|---|---|---|
| 예: 키를 평문 커밋하지 않는다 | `secret-guard.sh` PreToolUse 차단 | 2026-06 Gemini 키 유출 |

대표님이 교정하면 실수를 고치고 규칙을 더한다. 규칙이 이미 있었는데 강제하는 게 없었다면 **반복**이니 같은 변경 안에서 가장 높은 단계로 막는다. 실수가 일어날 수 없게 되면 그 문서 규칙은 지운다(표에는 장치를 남긴다).

**답변 (한국어):** 부류마다 근거(커밋·이슈·교정 기록), 고른 단계, 더 높은 단계가 왜 안 됐는지, 증명(proof). 허용한 예외 목록(사유·만료일)은 따로 모아 적는다.
