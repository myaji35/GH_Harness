2. 반복된 결함 패턴 3가지

패턴 A — "실패를 성공으로 위장하는 mock" (7개 프로젝트)

외부 호출이 실패하면 하드코딩된 값을 반환하고, 호출자는 그것이 실패인지 알 수 없다.

프로젝트위장된 값결과
LandCheckmock_land 500㎡ × 350,000원모든 필지가 동일한 1억 7,500만원 참고가액
CEOmock_result level:4허구의 "CEO 네트워킹 식대 50만원" 긴급 알림 발송
SocialDoctorsMath.random() 도달 500~5,500조작 수치가 성과 데이터로 표시
OmniVibePro_generate_fallback 템플릿"기본 전략/일반/Brand" 더미를 200 OK로 반환
InsureGraphrand(-1.0..1.0) 1536차원랜덤 벡터를 임베딩으로 저장 (죽은 코드)
ExamsGraphconcept_gap_prob = 0.5하드코딩 0.5가 가중치 80%로 학습 진단 반영
CPOFlow2IN_PRICE.to_f → 0.0단가 결측이 AED 0.00으로 카탈로그 표시
공통점 — mock 값이 구체적이다. nil이나 빈 값이 아니라 그럴듯한 숫자·문장이어서 진짜와 구별되지 않는다.

패턴 B — "출처를 알려주고도 버리는 UI" (3개 프로젝트)

API는 source: 'mock' 같은 마커를 보내는데 화면이 그 필드를 참조하지 않는다.

  • SocialDoctors — InsightsResponse에 source가 있으나 프론트 InsightsData 타입에 애초에 선언조차 없어 값이 버려짐
  • CEO — Disclaimer 모듈이 존재하나 attach/wrap 호출부가 grep 0건 (죽은 코드)
  • Townin — forecast는 fallback: true를 잘 표기하는데, AEO 리라이트는 source 필드 자체가 없음

시사점 — 백엔드가 정직해도 프론트가 버리면 사용자에겐 거짓말이다. 양쪽을 함께 봐야 한다.

패턴 C — "실패해도 돈은 빠진다" (3개 프로젝트)

프로젝트결함상태
LandCheck차감 → 분석 순서, 트랜잭션 없음수정 완료
TowninAEO 유료 리라이트 실패해도 크레딧 영구 차감 (status 미필터)미처리 P0
TowninTOSS_SECRET_KEY 미설정 시 결제 검증 없이 자동 승인미처리 P0

Townin의 두 번째 건은 방향이 반대다 — 돈을 안 받고 크레딧을 주는 구조로, 운영에서 환경변수가 비면 즉시 손실이 발생한다.

금전 정합은 대체로 견고했다. SocialDoctors의 Toss 결제·커미션은 트랜잭션 원자성과 검증 순서(외부 승인 → DB 반영)가 지켜져 있었고, ExamsGraph의 환불도 즉시 완료가 아닌 refund_requested 상태 전이로 올바르게 설계돼 있었다. OmniVibePro의 quota는 응답 성공 시에만 차감한다. 결제는 신경 써서 만들었다는 뜻이다.

InsureGraph는 로깅·사용자 인지 2문항 모두 "위반 없음" — 유일한 결함이 호출되지 않는 죽은 코드였다. OCR 실패를 ocr_status: failed + 에러 메시지로 화면에 그대로 노출하는 구조가 모범적이다.

infraGrid의 결함은 성격이 다르다. 결측 텔레메트리를 to_f로 0 변환해 그래프에 그리면, 센서 미보고 구간이 "온도 급락"처럼 보인다. 인프라 모니터링에서 이건 장애 오판으로 직결된다.

판정 기준 — "모르는 것을 아는 척하는 값을 내보내면 안 된다."
nil·"조회 불가"는 정직한 출력이고, 평균값·기본값·mock은 거짓 정보다. 특히 그 값이 금액·점수·판정으로 이어지면 결함이 아니라 책임 문제가 된다.
순서 고정 — ① 폴백 정책 확정 → ② 워터폴·캐시로 실패 확률 축소.
폴백을 정하지 않고 공급사를 늘리면 전부 실패했을 때 여전히 가짜 값이 나온다. 비용만 늘고 문제는 그대로다.

이제 어느 프로젝트에서든 외부 API 코드를 건드리면 이 4문항이 컨텍스트에 자동 로드된다.

7. 이 점검이 시작된 경위

대표님이 요청한 것은 "LandCheck 워터폴 적용 시나리오"였다. 워터폴 설계에는 반드시 정해야 할 항목이 하나 있다 — "전부 실패하면 어떻게 되는가", 즉 폭포의 마지막 칸이다.

그 자리를 확인하러 코드를 열었더니 이미 채워져 있었다. mock_land로.

워터폴이라는 개념이 결함을 탐지한 것이 아니라, 워터폴을 설계하려면 반드시 봐야 하는 위치에 결함이 있었다. 그 질문을 30개 프로젝트로 확장한 것이 이 점검이다.
